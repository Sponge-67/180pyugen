180pyugen — Info

This page describes the complete conversion pipeline, how stereo alignment differs from simple 2-D image shifting, where the camera/lens model is applied, and which options affect quality or performance.

1. System overview

180pyugen converts a synchronized pair of fisheye cameras into VR180 side-by-side equirectangular output. Each eye occupies a square 180° × 180° field. The two eye squares are packed side by side to produce the familiar 2:1 stereo frame.

The central design principle is that lens correction and stereo alignment are separate operations. The lens profile converts between fisheye image radius and 3-D ray angle. A/B correspondence points recover the relative 3-D orientation between cameras. Keeping those problems separate makes the renderer more stable and prevents a local 2-D correction from being mistaken for camera calibration.

2. Still-image pipeline

  1. Decode: read left and right source rasters. OpenCV is the normal decoder; Pillow can be used diagnostically on desktop.
  2. Resolve profiles: determine 180° radius, optical center and projection function independently for each eye.
  3. Pixel → ray: convert A/B source pixels into normalized 3-D viewing rays using the inverse fisheye projection.
  4. Stereo rotation: align right A to left A using the shortest Rodrigues rotation, then rotate around A so right B agrees with left B.
  5. Output ray field: generate a 180° × 180° equirectangular direction for every destination pixel.
  6. Zenith correction: apply roll, pitch and yaw in 3-D.
  7. Ray → fisheye: project each destination ray back into the relevant source image.
  8. Sample and pack: sample left/right sources, create one square eye per view, then pack them side by side.

3. Video pipeline

Video uses the same geometry but separates one-time setup from per-frame work. When both movies are selected, the browser now uploads/probes them and automatically displays the current left/right reference frames. The explicit Load reference frames button remains useful after changing the frame numbers.

  1. Probe both movies for resolution, frame count, FPS and codec.
  2. Choose synchronized reference frame numbers.
  3. Display those frames and choose/match A/B.
  4. Compute stereo rotation, zenith rotation and complete source-coordinate maps once.
  5. Seek to the requested start frames and then decode sequential frame pairs.
  6. Reuse the precomputed remap for every frame pair.
  7. Apply optional final right-eye convergence/vertical trim.
  8. Encode the resulting SBS frame to the selected codec.

Because map construction is removed from the frame loop, ordinary conversion is much faster than repeatedly invoking a complete still-image renderer.

4. Camera/lens model

A profile defines three things: the radius corresponding to a 90° off-axis ray, the optical-axis coordinate, and the radial projection function. Supported models include orthographic, equisolid, arbitrary y=A·sin(kθ), and custom piecewise modes.

180Augen and 180Kino custom mode 3 are intentionally distinguished. The supplied 180Kino profiles/documentation use a piecewise quadratic y=aθ²+bθ+c; the recovered 180Augen executable follows a different custom expression. The program preserves that distinction rather than forcing both profile families through one approximation.

5. A/B matching and 3-D stereo alignment

A/B should normally be placed on distant, high-contrast structure with relatively little parallax and a useful angular separation. In the reconstructed still workflow, 180Augen uses a 20×20 TM_SQDIFF template; 180Kino uses 20×20 TM_SQDIFF_NORMED. Lower score is better in both cases.

Matching only identifies corresponding pixels. The important correction happens after those pixels are converted to rays: a 3-D rotation aligns the camera coordinate systems. That differs from simply translating one flat picture over the other.

6. Stereo Align inspector

The alignment inspector now defaults to Perceptual fuse, which is the best flat-screen proxy of what the final stereo pair will look like after the current convergence/vertical-trim candidate is applied. Negative Align, alpha blend, difference and red/cyan anaglyph remain available as diagnostic views. Apply to output writes the candidate directly into the real final stereo render.

If the final projected output still contains a small global residual disparity, use right-eye convergence X or vertical trim Y. These operate in VR degrees on the rendered right eye. Large corrections usually indicate that A/B selection or lens calibration should be revisited instead.

Fast mode can convert floating maps into OpenCV's fixed-point representation once, reducing map memory traffic. OpenCV often runs its own threads, so 180pyugen avoids blindly adding another eye-level thread layer when that would oversubscribe the CPU.

8. Video encoding and timing

HEVC/H.265 is the native-oriented video choice. Software HEVC is reproducible on ordinary systems; HEVC NVENC can offload encoding to supported NVIDIA hardware. Encoding acceleration is separate from fisheye remapping—the geometry remains a CPU/OpenCV operation in the portable path.

The 180Kino timing option rounds the source frame rate in the manner observed in the supplied native output (for example approximately 59.94 fps → 60 fps). Preserve-source mode keeps the reported input FPS instead. Audio is not currently muxed by the compatibility path.

9. Web/server architecture

The browser handles interaction: local file selection, previews, point picking, Stereo Align visualization, job progress and result playback. Python/FastAPI remains authoritative for decoding server-side media, native-style matching, profile evaluation, geometry, rendering and encoding.

Files are stored in temporary session directories. Development mode uses an inline background executor. A production deployment can use Redis/RQ warm workers so long 4K/8K jobs do not block HTTP request handling. Repeated renders reuse the already-uploaded video pair until the session expires or is deleted.

10. Native parity status

180pyugen is a clean-room reconstruction rather than the original source. Several still-image behaviors have been recovered and quantitatively validated against native 180Augen output. The original 180Kino used CUDA and a GPU conversion kernel, so exact video pixel parity remains an explicit comparison target. The application therefore exposes separate performance and native-comparison modes instead of claiming that every optimized path is instruction-identical.
